# Go Marketplace

Backend маркетплейса на Go с микросервисной архитектурой. Проект предоставляет HTTP API для управления пользователями и товарами, а также отдельный сервис аутентификации. Сервисы используют PostgreSQL для хранения данных, межсервисное взаимодействие осуществляется по gRPC. База данных и мигратор поднимаются в контейнерах с помощью Docker Compose.

## Фичи

### users
- Получение списка пользователей и отдельного пользователя.
- Создание, частичное обновление (PATCH) и удаление пользователя.
- Роли `buyer`, `seller` и `admin`.
- Оптимистическая блокировка изменений через поле `version`.

Операции управления пользователями доступны только администраторам за исключением создания посредством регистрации. При регистрации клиент обращается к сервису `auth`, пользователь создается через gRPC-вызов в основном сервисе.

### products
- Получение списка товаров и отдельного товара.
- Создание, частичное обновление (PATCH) и удаление товара.
- Привязка товара к продавцу по внешнему ключу `seller_id`.
- Оптимистическая блокировка обновлений через `version`.

Просматривать товары можно без Access-токена. Создавать, изменять и удалять товары могут пользователи с ролью `seller`.

### auth
- Регистрация с созданием пользовательского профиля.
- Вход по логину и паролю.
- Генерация пары Access- и Refresh-токенов.
- Ротация Refresh-токена.
- Отзыв refresh-токена при выходе.
- Хеширование паролей и хранение хешей Refresh-токенов.
- Подписание Access-токенов ассимитричным алгоритмом RS256 для возможности проверки токенов публичным RSA-ключом другими сервисами в middleware.

## Архитектура

Приложение состоит из двух независимо запускаемых процессов: api и auth.

```text
                   Клиент 
                      │ HTTP
             ┌────────┴────────┐
             ▼                 ▼
       ┌───────────┐      ┌──────────┐
       │    api    │      │   auth   │
       │           │ gRPC │          │
       │ /users    │◄─────│  /auth   │
       │ /products │      │          │
       └───────────┘      └──────────┘
             └────────┬─────────┘
                      ▼
                  PostgreSQL
```

### `cmd/api`

Запускает основной API:
- HTTP-сервер с маршрутами `/users` и `/products`;
- gRPC-сервер `UserService`, который используется сервисом `auth`;
- JWT middleware для защищенных HTTP-маршрутов;
- подключение к PostgreSQL.

### `cmd/auth`

Запускает auth-сервис:
- HTTP-маршруты `/auth`;
- gRPC-клиент для обращения к сервису пользователей;
- работа с учетными данными и Refresh-токенами в PostgreSQL;
- выпуск Access-токенов.

Оба сервиса подключаются к одной базе данных, но не имеют доступа к таблицам друг друга. Профиль пользователя и его учетные данные логически разделены: профиль хранится в таблице `users`, а логин и хеш пароля — в `credentials`.

### Слои функциональности

В пакетах `internal/features/{auth,users,products}` применяется разделение на:
- `handler` — HTTP-обработчики, DTO и структурная валидация;
- `service` — бизнес-логика и структурная валидация;
- `repository` — операции с PostgreSQL;
- `grpc` — gRPC-клиент или сервер там, где он нужен.

Общие доменные модели, sentinel ошибки, подключение к БД, логирование, безопасность и middleware, используемые несколькими сервисами, находятся в `internal/core`.

- Go версии, совместимой с директивой `go` в `go.mod`;

## Настройка окружения

Файл `.env` должен находиться в корне проекта, в качестве примера приведен `.env.example`.

| Переменная | Назначение |
|---|---|
| `SERVER_PORT` | Порт HTTPS-сервера `api` |
| `AUTH_SERVER_PORT` | Порт HTTPS-сервера `auth` |
| `SERVER_READ_TIMEOUT` | Тайм-аут чтения HTTP-запроса, например `5s` |
| `SERVER_WRITE_TIMEOUT` | Тайм-аут записи HTTP-ответа, например `10s` |
| `SERVER_IDLE_TIMEOUT` | Тайм-аут простоя HTTP-соединения, например `60s` |
| `TLS_CERT_PATH` | Путь к TLS-сертификату |
| `TLS_KEY_PATH` | Путь к приватному ключу TLS |
| `POSTGRES_USER` | Пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL |
| `POSTGRES_HOST` | Хост PostgreSQL, доступный из процессов Go |
| `POSTGRES_DB` | Имя базы данных |
| `LOGGER_LEVEL` | Уровень логирования: `debug`, `info`, `warn` или `error` |
| `LOGGER_FORMAT` | Формат логов: `text` или `json` |
| `AUTH_ISSUER` | Значение `iss`, которое используется при создании и проверке JWT |
| `AUTH_PUBLIC_KEY_PATH` | Путь к публичному RSA-ключу |
| `AUTH_PRIVATE_KEY_PATH` | Путь к приватному RSA-ключу для подписи JWT |
| `AUTH_ACCESS_TTL` | Время жизни access-токена, например `15m` |
| `AUTH_REFRESH_TTL` | Время жизни refresh-токена, например `720h` |
| `GRPC_PORT` | Порт gRPC-сервера `UserService` в `api` |
| `GRPC_ADDR` | Адрес gRPC-сервера, доступный сервису `auth` |
| `PROJECT_ROOT` | Абсолютный путь к корню проекта; Makefile переопределяет его текущим каталогом |

`POSTGRES_HOST` и `GRPC_ADDR` зависят от способа запуска. При запуске Go-процессов на хосте используется `localhost:<порт>`. Если сервисы будут запускаться внутри сети в рамках Docker Compose, нужно использовать имена сервисов и соответствующие внутренние порты.

Приложения вызывают `godotenv.Load()` и завершаются с ошибкой, если `.env` не удалось загрузить. Для переменных, которые разбираются как длительности, необходимо использовать формат Go `time.ParseDuration`, например: `5s`, `1m`, `15m`.

### RSA-ключи для JWT

Создание приватного и на его основе публичного ключей:

```bash
openssl genrsa -out private.pem 2048
openssl rsa -in private.pem -pubout -out public.pem
```

Их пути нужно укакзать в `.env`.

## Запуск PostgreSQL и миграций

Makefile импортирует `.env`, поэтому файл должен существовать до вызова `make`.

Запустить PostgreSQL:
```bash
make pg-up
```

Остановить PostgreSQL:
```bash
make pg-down
```

Применить миграции:
```bash
make migrate-up
```

Откатить последнюю миграцию:
```bash
make migrate-down
```

Создать новую последовательную пару файлов миграции:
```bash
make migrate-create
```

`make pg-erase` удаляет каталог `out/pgdata` после остановки контейнера. Это удалит данные БД, поскольку эта директория является томом контейнера.

Миграции находятся в `migrations/`. 

## Запуск сервисов

После настройки `.env`, ключей, PostgreSQL и миграций нужно запустить два процесса в отдельных терминалах из корня проекта:

Основной сервис:
```bash
go run ./cmd/api/main.go
```

Сервис auth:
```bash
go run ./cmd/auth/main.go
```

Оба процесса используют `.env`. `api` поднимает HTTPS и gRPC-сервер, `auth` поднимает HTTPS и подключается к gRPC-серверу.

`docker-compose.yaml` описывает контейнеры PostgreSQL и мигратора.

## HTTP API

Все тела запросов и ответы API передаются в JSON в теле HTTP запросов и ответов. Для запросов с телом необходим заголовок `Content-Type: application/json`. Хэндлеры ограничивают размер тела запроса 1 МБ и запрещают неизвестные JSON-поля.

В примерах ниже предполагается, что `localhost:8080` — адрес HTTPS-сервера основного сервиса, а `localhost:8081` — адрес HTTPS-сервера сервиса `auth`. 

### Аутентификация

#### `POST localhost:8081/auth/register`

Создает профиль пользователя, учетные данные и возвращает пару токенов.

Пример запроса:

```json
{
  "name": "Alex",
  "phone": "79991234567",
  "login": "alex",
  "password": "strong-password",
  "role": "buyer"
}
```

`phone` может быть `null` или строкой. Допустимые роли профиля — `buyer`, `seller`, `admin`.

Успешный ответ: `201 Created`.

```json
{
  "access_token": "<access-token>",
  "refresh_token": "<refresh-token>"
}
```

#### `POST localhost:8081/auth/login`

Выполняет вход по логину и паролю.

```json
{
  "login": "alex",
  "password": "strong-password"
}
```

Успешный ответ: `200 OK` с `access_token` и `refresh_token`.

#### `POST localhost:8081/auth/refresh`

Принимает действующий refresh-токен, проверяет его состояние, отзывает старый токен в рамках ротации и выдает новую пару.

```json
{
  "refresh_token": "<refresh-token>"
}
```

Успешный ответ: `200 OK` с новой парой токенов. После успешной ротации используйте новый refresh-токен.

#### `POST localhost:8081/auth/logout`

Отзывает refresh-токен.

```json
{
  "refresh_token": "<refresh-token>"
}
```

Успешный ответ: `204 No Content`.

### Товары

#### `GET localhost:8080/products`

Возвращает список товаров. Доступен без аутентификации.

#### `GET localhost:8080/products/{id}`

Возвращает товар по идентификатору. Доступен без аутентификации.

#### `POST localhost:8080/products`

Создает товар. Требуется access-токен с ролью `seller`.

Пример заголовка:

```http
Authorization: Bearer <access-token>
Content-Type: application/json
```

Пример тела:

```json
{
  "name": "Keyboard",
  "description": "Mechanical keyboard",
  "price": 7500
}
```

Идентификатор продавца определяется из проверенного access-токена, а не должен задаваться клиентом.

#### `PATCH localhost:8080/products/{id}`

Частично обновляет товар. Требуется роль `seller`. В модели обновления доступны `name`, `description` и `price`; `seller_id` не входит в набор изменяемых полей.

Для поля `description` различаются отсутствие поля, строковое значение и `null`. Реализация `Nullable[T]` позволяет обработать явное обнуление nullable-поля отдельно от отсутствующего поля.

#### `DELETE localhost:8080/products/{id}`

Удаляет товар. Требуется роль `seller`.

## Аутентификация и авторизация

### Access-токен

- Выпускается сервисом `auth`.
- Подписывается алгоритмом RS256.
- Содержит идентификатор пользователя в `sub`, роль пользователя `role` и другие зарегистрированные JWT claims.
- Проверяется сервисом `api` с помощью публичного RSA-ключа.
- Проверка включает алгоритм подписи, `issuer`, срок действия и роль.

Клиент передает токен в заголовке:

```http
Authorization: Bearer <access-token>
```

Middleware извлекает `user_id` и роль из claims и помещает их в контекст запроса `*http.Request`. Маршруты с ограничением роли используют эти данные для авторизации.

### Refresh-токен

Refresh-токен используется для получения новой пары токенов. В базе хранится не исходное значение, а его хеш. При обновлении происходит ротация токена – при логауте он помечается отозванным. Истекший, отсутствующий или отозванный refresh-токен не принимается.

### Пароли

Пароли хешируются алгоритмом bcrypt, в таблице `credentials` хранится хэш пароля `password_hash`. Сервисная валидация ограничивает длину пароля диапазоном 8–72 байта из-за реализации алгоритма.

## Модели данных

### `users`

| Поле | Назначение |
|---|---|
| `id` | Первичный ключ |
| `version` | Версия записи для оптимистической блокировки |
| `name` | Имя пользователя, длина 2–50 символов |
| `phone` | Необязательный телефон, только цифры по ограничению БД |
| `role` | `buyer`, `seller` или `admin` |
| `created_at` | Время создания |

### `products`

| Поле | Назначение |
|---|---|
| `id` | Первичный ключ |
| `version` | Версия записи |
| `name` | Название, длина 3–50 символов |
| `description` | Необязательное описание |
| `price` | Положительная цена в целых единицах |
| `created_at` | Время создания |
| `seller_id` | Внешний ключ на `users.id` |

Удаление пользователя, на которого ссылаются товары, ограничено внешним ключом `ON DELETE RESTRICT`.

### `credentials`

Связывает пользователя с уникальным логином и хешем пароля. `user_id` одновременно является первичным ключом и внешним ключом на `users.id`.

### `refresh_tokens`

Хранит хеш refresh-токена, пользователя, срок действия, время создания и необязательное время отзыва. При удалении пользователя связанные учетные данные и refresh-токены удаляются каскадно.

### Оптимистичная блокировка

В таблицах `users` и `products` есть поле `version`. При конкурентном изменении репозиторий обновляет запись с учетом ожидаемой версии. Если запись не обновлена из-за того, что версия уже изменилась или запись исчезла, сервис возвращает клиенту 409 Conflict. В таком случае клиенту следует получить актуальное состояние объекта и повторить операцию.

## Protobuf и gRPC

Контракт находится в `proto/users.proto`. Сейчас `UserService` предоставляет два unary RPC вызова:

- `CreateUser` — создает пользовательский профиль, возвращает ID и роль;
- `GetUserRole` — возвращает роль пользователя по ID.

gRPC-ошибки преобразуются в sentinel-ошибки в файле `internal/core/transport/grpc_errors`. Для возможности различать природу ошибок одного типа конкретная причина ошибки передается в теле ошибки в поле `details` согласно рекомендации Google: https://google.aip.dev/193.

## Обработка ошибок

Для HTTP используется структура `ResponseHandler`. В HTTP ответе ошибки представлены JSON-объектом с полем `error`:

```json
{
  "error": "invalid request body"
}
```

Используемые группы HTTP-статусов:
- `400 Bad Request` — некорректный ввод, параметры или тело запроса;
- `401 Unauthorized` — отсутствующий или недействительный access-токен;
- `403 Forbidden` — недостаточная роль;
- `404 Not Found` — объект не найден;
- `409 Conflict` — конфликт версии или занятый логин;
- `500 Internal Server Error` — непредвиденная ошибка.

Конкретный статус определяется путем сопоставления с sentinel ошибкой в `internal/core/transport/response/handler.go`.

## Замечания

- Сервис `api` должен получать только публичный ключ JWT; приватный ключ нужен `auth` для подписи.
- Поскольку `api` и `auth` используют общую БД, это разделение процессов и ответственности, но пока что не полная изоляция данных на уровне отдельных баз.
